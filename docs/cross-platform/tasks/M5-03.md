# M5-03 — `SecretStore` per platform + full clone detection

GitHub issue: #12. Spec: `docs/p2p-sync/PLAN.md` § Identity (per-peer keys stored encrypted with a device-bound key; a DB restored onto another device ⇒ decryption fails ⇒ **regenerate `deviceId`** and mark all peers re-pair). Interface: `shared/src/commonMain/kotlin/com/yogeshpaliyal/deepr/p2p/node/SecretStore.kt` (M5-01).

## Part A — common: one AES-GCM store, platform key providers
- Rename/generalize `InMemorySecretStore` into `class AesKeySecretStore(crypto: P2pCrypto, key: ByteArray)` (same nonce‖ciphertext format, `open` returns null on any failure). Keep `InMemorySecretStore(crypto)` as a one-line subclass/factory with a random key so existing tests compile unchanged.
- `P2pNode`: when `secrets.open(keyEnc)` returns null, besides `markAllPeersNeedRepair()`, regenerate the device identity once: new query `regenerateDeviceId: UPDATE SyncDevice SET deviceId = ? WHERE id = 1;` with a fresh random 16-byte hex id (same format as the schema default). Only regenerate if at least one peer row exists and none could be opened (so a single corrupt row doesn't change identity). Extend the clone test in `P2pNodeTest` to assert `deviceId` changed.

## Part B — desktop (`desktopApp`, or `shared/src/jvmMain` if you prefer it next to other jvm-only code)
`class FileKeySecretStore(file: File, crypto: P2pCrypto)`: reads a 32-byte key from `file`, or creates it with `SecureRandom` on first use. Create with owner-only permissions **before** writing the key (`Files.createFile` with `PosixFilePermissions.asFileAttribute(rw-------)` where POSIX is supported; on Windows rely on the user profile ACL and say so in a comment). Delegates to `AesKeySecretStore`. File: `<appDataDir>/p2p-secret.key`.
DECISIONS.md: add **D12 — desktop secret key in a 0600 file** (why not an OS keychain: no KMP/JVM keychain library without native deps across Linux/macOS/Windows; risk: anyone with the user's account can read it, same as the DB itself).
Tests (`desktopApp/src/test` or `shared/src/jvmTest`): roundtrip; a second instance on the same file opens what the first sealed; a different file ⇒ `open` returns null; on POSIX the file mode is exactly `rw-------`.

## Part C — Android, `shared/src/androidMain/kotlin/com/yogeshpaliyal/deepr/p2p/node/KeystoreSecretStore.kt`
AES-256-GCM key in `AndroidKeyStore`, alias `deepr_p2p_secret`, `PURPOSE_ENCRYPT or PURPOSE_DECRYPT`, `BLOCK_MODE_GCM`, `ENCRYPTION_PADDING_NONE`, created on first use (non-exportable). `seal`: `Cipher.getInstance("AES/GCM/NoPadding")` init ENCRYPT (let the Keystore pick the IV) ⇒ `iv(12) ‖ ciphertext+tag`. `open`: split, init DECRYPT with `GCMParameterSpec(128, iv)`; any exception ⇒ null. (Keystore can't be unit-tested on the JVM: keep it small and obviously correct.)

## Part D — iOS, `shared/src/iosMain/kotlin/com/yogeshpaliyal/deepr/p2p/node/KeychainSecretStore.kt`
A 32-byte random key stored as a Keychain generic password (`kSecClassGenericPassword`, service `com.yogeshpaliyal.deepr.p2p`, account `secret-key`, `kSecAttrAccessible = kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` — ThisDeviceOnly so it never migrates in backups, which is what makes clone detection work). Read with `SecItemCopyMatching`, else generate (`SecRandomCopyBytes`) and `SecItemAdd`. Delegates to `AesKeySecretStore(crypto, key)` where `crypto` is passed in (the iOS `P2pCrypto` comes in M5-04). Use Kotlin/Native CoreFoundation interop (`CFDictionaryCreateMutable`, `CFBridgingRetain`/`CFBridgingRelease` or `NSDictionary` toll-free bridging); free what you create. **This can't be compiled here**: keep it minimal; the orchestrator fixes compile errors from CI.
iOS test `shared/src/iosTest/.../KeychainSecretStoreTest.kt`: two instances share the key (seal with one, open with the other), using `InMemorySecretStore`'s crypto stand-in is not possible on iOS yet ⇒ test only that the 32-byte key read twice is identical (expose an `internal fun loadOrCreateKey(): ByteArray`).
