# M5-09 — iroh in pairing and peers: invite field, peer column, LAN-then-iroh dialling, app wiring

GitHub issue: #12. Decision D14 + `docs/p2p-sync/PLAN.md` P-1 (user-approved). Builds on M5-08: `shared/src/jvmShared/kotlin/com/yogeshpaliyal/deepr/p2p/iroh/IrohTransport.kt` (`start/stop`, `ticket`, `post(ticket, path, body)`), frames in `commonMain/.../p2p/iroh/IrohFrames.kt`. Read the M5-08 Review note: `handle()` currently writes `remoteHost = "iroh:<id>"` into the LAN host field — fix that here. Envelope crypto, pairing MACs/SAS and merge rules stay unchanged.

## Part A — wire format (backward compatible)
- `Invite` (`p2p/core/Pairing.kt`): add `val i: String? = null` = the inviter's iroh `EndpointTicket` string. Not part of the transcript/MAC (the SAS still protects pairing). Old invites without `i` must decode; old apps ignore it (`ignoreUnknownKeys`).
- `JoinRequest`: add `val i: String? = null` = the joiner's ticket, so the inviter can dial the joiner later.
- Authenticated hello body: today `"{}"`; send `{"i":"<my ticket>"}` (sealed like now) so a peer whose ticket changed (relay change) updates it; the receiver stores it when present.

## Part B — schema: migration `shared/src/commonMain/sqldelight/migrations/12.sqm` (mirror in `Deepr.sq`)
- `ALTER TABLE SyncPeer ADD COLUMN irohTicket TEXT NOT NULL DEFAULT '';`
- `ALTER TABLE SyncDevice ADD COLUMN irohKeyEnc BLOB;` (this device's iroh secret key, sealed with `SecretStore` like pair keys ⇒ a cloned DB can't reuse the identity; on open failure generate a new key).
- Queries: `updatePeerIroh(irohTicket, peerId)`, `getIrohKey`, `setIrohKey`. SQLite 3.9-compatible. Check `tools/sync-harness` (it compiles Deepr.sq + migrations; its MigrationTest may need the new version) stays green.

## Part C — `P2pNode` dialling
- New common interface `p2p/node/IrohLink.kt`: `val ticket: String?`, `suspend fun post(ticket: String, path: String, body: String): HttpReply`. `IrohTransport` implements it. `P2pNode` gets `var iroh: IrohLink? = null` (set after construction: the transport needs the node for `handle`, so no constructor cycle).
- One private `postToPeer(host, port, irohTicket, path, body)`: try LAN first when `host` is non-empty and `port > 0` (keep a **short** LAN attempt: wrap in `withTimeout(3 s)` so an off-network peer doesn't cost 30 s), then iroh when `irohTicket` is non-empty and `iroh != null`; throw the last error otherwise. Use it in the sync transport, `notifyPeer`, and `completeJoin`'s hello polling (the joiner uses `invite.h`/`invite.p` and `invite.i`). `join()`'s `/pair` POST: LAN hosts first (3 s each), then `invite.i`.
- Persist tickets: joiner stores `invite.i` in the new peer row; inviter stores `JoinRequest.i` on `confirmPairing`; any authenticated hello carrying `i` updates it. `syncPeer`/`syncAll`/`notifyPeer` must no longer skip peers with port 0 when they have an iroh ticket (that's what lets the inviter initiate sync now).
- `handle(path, body, remoteHost)`: only call `updatePeerAddress` for LAN hosts; never for `"iroh:…"`.
- `startInvite(profileId, hosts, port)` → also put `iroh?.ticket` into the invite.

## Part D — wiring
- `P2pSyncController`: start/stop the iroh link together with the HTTP server (if one is configured); `startInvite` includes the ticket.
- `p2pModule(crypto, secrets, irohFactory: ((P2pNode) -> IrohLink)? = null)` (or similar): Android and desktop pass a factory building `IrohTransport` with the key from `SyncDevice.irohKeyEnc` (sealed/opened via `SecretStore`) and a `scope`; iOS passes null until M5-10.
- Sync settings screen: in each peer row show how it's reachable ("Wi-Fi", "Internet", or both) from `lastPort`/`irohTicket` — small text, new English strings.

## Tests (JVM, real iroh like `IrohTransportTest`)
`shared/src/jvmTest/.../p2p/iroh/IrohPairingTest.kt`: two nodes whose LAN `HttpPost` always fails (simulates different networks), each with a real `IrohTransport`: invite (with `i`) → join → confirm → completeJoin succeed over iroh; a link on A reaches B via B's `syncPeer`, **and** a link on B reaches A via A's `syncPeer` (inviter-initiated, using the joiner's ticket). Plus: an invite without `i` still decodes; `handle` with `"iroh:…"` doesn't touch `lastHost`; restart with the sealed iroh key keeps the same endpoint id. Existing P2pNode/controller/loopback tests stay green.
